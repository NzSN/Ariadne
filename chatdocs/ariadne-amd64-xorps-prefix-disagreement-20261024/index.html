Why does AMD’s XORPS entry contain the XORPD prefix?

Update · 24 October 2026: Vol3 is the selected authority for this case. The current rule is 0F 57 /r → XORPS and 66 0F 57 /r → XORPD. The checked projection preserves the conflicting Vol4 rows. The source comparison below explains the original disagreement; the selection is now implemented. Current contract and limits.

The opcode map distinguishes the instructions by 66h. The detailed XORPS entry prints the prefixed pattern as well. Those two descriptions do not give us one reconciled rule for the legacy XORPS form.

The disputed property is opcode selection. For these SIMD forms, 66h is part of the instruction’s identity. It does not reduce the operation to 16 bits. The earlier fixed-64 near-branch hypothesis does not decide this separate rule.

2. Why “ignore the 16-bit override” does not resolve it

Role of 66hMeaningRelation to this case
Operand-size overrideChanges the data-size choice when the instruction’s rules permit it.The earlier near-branch scope decision excluded a possible operand-16 alternative for seven selected branch groups.
Mandatory opcode selectorDistinguishes a particular instruction/form inside an opcode map.This is the disputed XORPS/XORPD role. Both legacy rows describe a 128-bit XMM operation.
Address-size overrideChanges the applicable address calculation.That is a separate 67h rule; it is not the XORPS/XORPD identity question.

Deleting 66h because the target executes in native 64-bit mode would therefore skip the very distinction being reviewed. A prefix can remain meaningful in that mode even when it is not selecting a smaller operand.

The general opcode-extension role is stated in selected Vol3’s operand-prefix discussion, PDF 51. The report applies that role to the exact compared rows; it does not establish legality for every additional prefix combination.

/r is source-table notation for a ModRM-based operand form. It is not an instruction byte. The patterns here are encoding descriptions, rather than a newly decoded or executed concrete instruction sequence.

4. Why the XOR result cannot settle the disagreement

“PS” groups the 128-bit legacy operand as four 32-bit lanes; “PD” groups it as two 64-bit lanes. These XOR instructions apply a Boolean operation to the bits. They do not convert or add floating-point values.

For the same two 128-bit inputs, regrouping bits into different lane widths leaves the bitwise XOR result unchanged. Here is a pure arithmetic illustration:

A = 0123456789ABCDEF0123456789ABCDEF
B = F0F0F0F0F0F0F0F0F0F0F0F0F0F0F0F0
A XOR B =

The page computes that hexadecimal XOR locally. It does not execute an x86 instruction or test a processor.

Consequently, matching output bits would not tell us which source encoding row was intended. The selected instruction descriptions also list different legacy feature families: SSE for XORPS and SSE2 for XORPD. Instruction identity, feature requirements and encoding classification still need their own source contracts.

Instruction descriptions and support tables: XORPS, PDF 1821 and XORPD, PDF 1818. The equality argument above is Boolean reasoning about supplied values; it is not a native qualification result.

The VEX and EVEX rows are separately encoded forms. In the compared entries, their pp fields distinguish the PS and PD variants. They are useful context, but they do not by themselves correct a legacy encoding literal.

What remains to establish

The choice is not an AMD erratum and does not rewrite the source literal, prove every physical CPU’s behavior or authorize arbitrary prefix combinations. Runtime and whole-ISA qualification retain their own gates.

A publisher correction or authoritative interpretation could instead settle the intended source rule. None is established by the current record.

Why the preference is plausible, as an inference: the Vol3 map explicitly separates the prefix bands and provides a coherent distinction between the two legacy names. The user has selected that source rule for this case. The current-scope checker now applies it while preserving the Vol4 literals. This does not create blanket Vol3 precedence for other source questions.
