# BAP Stage 1 projection: pinned source review

## Context and follow-up

**Status.** Pinned source and finite-corpus review; not a universal ISA proof.

**Why this document exists.** [Projection design](bap-semantic-backend-design.md) requires typed BIL, correct aliases and conservative effects.

**What this document establishes.** This review binds projection assumptions to the selected legacy x86 lifter, typed C API and finite corpus. It explains alias, extraction, memory and unknown-value handling.

**Where to go next.**

- [Delivery record](bap-only-removal-validation.md) — reports the exercised producer and adapter checks.
- [Trust boundary](semantic-assurance.md) — explains which lifter and projection claims remain conditional.

**What remains unresolved.** The review and corpus do not establish universal lifter correctness or all-opcode projection soundness. New forms require their own justified admission and negative controls.

For the wider context, see the optional [documentation map](../documentation-map.md).

**Decision question.** Which effects can Ariadne's optional AMD64 backend project from the selected BAP build into canonical byte GPR cells, flags, `memory:any`, and `state:other` without inventing semantics? This is a source review and diagnostic probe, **not** a projection acceptance or ISA proof. It applies the [Stage 1 plan](../../Plans/bap-integration.md) and [effect contract](operand-effects-design.md). The selected release is BAP `v2.5.0-alpha` at `baa9022`; its installed library reports `2.5.0-alpha` and CLI `2.5.0-alpha+baa9022`. The [official release](https://github.com/BinaryAnalysisPlatform/bap/releases/tag/v2.5.0) supplies the `libbap-dev_2.5.0.deb` C header, extracted locally at `tmp/bap-setup/stable/usr/local/include/bap.h`. Source links below pin `baa9022`.

## Provider and coverage boundary

**High confidence: pinned source and installed-library probes.** The x86 [`lifter` option](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_main.ml) defaults to `merge`; both probes below used an explicit mode. `modern` selects `IA32`/`AMD64`, whose [`x86_targets.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_targets.ml) fallback is `Ok []`. The [`x86_backend.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_backend.ml) dispatcher uses a registered opcode lifter or that fallback. The legacy [`x86_lifter.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_lifter.ml) likewise maps `No_semantics` to `Ok []`. In either mode, successful decode plus empty BIL establishes neither a no-op nor known fallthrough. The modern plugin registers selected forms, including [MOV](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_mov.ml); its small [x86-64 Lisp file](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/semantics/x86-64.lisp) does not establish general arithmetic/control coverage.

The **earlier modern selection diagnostic** called `bap_init2` with `--x86-lifter=modern`, required `llvm` and `x86` plugins, and decoded each string at `0x401000` with `bap_disasm_basic_next`. Nonempty BIL appeared for `4889d8` MOV64rr, `88d8` MOV8rr to AL, `88dc` MOV8rr to AH, `b878563412` MOV32ri, `488b448b08` MOV64rm, and `488903` MOV64mr. BIL was empty for `480fbec0` MOVSX, `0fb6c0` MOVZX, `4801d8` ADD, `4839d8` CMP, `4811d8` ADC, `480f45c3` CMOV, `488d4308` LEA, `50` PUSH, `58` POP, `7502` Jcc, `e800000000` direct CALL, `ffd0` indirect CALL, `c3` RET, `f00118` LOCK ADD, and `f3a4` REP MOVSB. It bounds modern-only arithmetic/control projection for those exact bytes, not all opcodes. It is **not a committed provider choice**.

The follow-up **explicit legacy diagnostic** used the same binary, plugins, VA, and corpus, with `--x86-lifter=legacy`. Every listed modern-negative form produced nonempty BIL; `48d1e0` SHL RAX,1, `48d3e8` SHR RAX,CL, and `48f7d0` NOT RAX did too. The [legacy source](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_lifter.ml) covers these classes. This shows broader sample coverage; semantic correctness still needs qualification.

## Typed BIL and C binding contract

**High confidence for AST shape; medium-high for getters, observed on this library.** The pinned [BIL AST](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/lib/bap_types/bap_bil.ml) defines `Load(mem,idx,endian,size)`, `Store(mem,idx,value,endian,size)`, `Let(var,definition,body)`, `Ite(condition,then,else)`, and statement `If(condition,true_stmts,false_stmts)` / `While(condition,body)`. The release header lists tags and generic getters but does not state how getters map to each constructor. Constructed-node C probes against its matching shared library gave:

| Tag | C getters observed | Projection consequence |
| --- | --- | --- |
| `LET` | `var` binder; `rhs` definition; `exp` body; `lhs` null | Scope binder; visit definition and body. |
| `ITE` | `exp` condition; `lhs` then; `rhs` else | Read condition; join alternatives. |
| `BINOP`, `CONCAT` | `lhs`, `rhs` operands | Visit both. |
| `UNOP`, `CAST`, `EXTRACT` | `exp` operand | Preserve bit ranges. `EXTRACT` numeric getters need the pinned mapping below. |
| `STORE` | `mem`, `addr`, `rhs` stored value; `exp` null | Visit address and data; retain old memory origins. |
| statement `IF` | `exp` condition, `true_stmts`, `false_stmts`; `stmts` null | Traverse both branches. AST assigns `stmts` to `WHILE`. |
| statement `JMP` | `jmp` target; `exp` null | Read an indirect target and retain typed control. |

The probe establishes behavior of this binary, not every BAP version. Lifted legacy CMOV, Jcc, SHL, CALL, RET, and REP MOVSB nodes confirmed the relevant `ITE`, `IF`, `JMP`, and `WHILE` accessors. Add getter regression fixtures to the helper. In particular, `bap_exp_lhs` for `LET` or `bap_stmt_stmts` for `IF` loses dependencies. The [AST](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/lib/bap_types/bap_bil.ml) also contains `Unknown` and `Special`; neither is evidence of a no-op.

**Critical `EXTRACT` mapping for this packaged C ABI.** The pinned [AST](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/lib/bap_types/bap_bil.ml) defines `Extract(hi,lo,exp)`, and the [expression printer](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/lib/bap_types/bap_exp.ml) displays `hi:lo[exp]`. Yet the *lifted* `88dc` MOV AH,BL has a printed `63:16[RAX]` whose C getters report `bap_exp_extract_hibit=16`, `bap_exp_extract_lobit=63`; its `7:0[RAX]` child reports `hibit=0`, `lobit=7`. A constructed `bap_exp_create_extract(8,15,var)` prints `15:8[var]` and reports `hibit=8`, `lobit=15`; passing `(15,8,var)` prints the invalid reversed range `8:15[var]`. This confirms swapped numeric positions in this C binding, not a memory-endianness effect. For a lifted node set `actual_hi = bap_exp_extract_lobit(e)` and `actual_lo = bap_exp_extract_hibit(e)`, then require `0 <= actual_lo <= actual_hi < operand_width`. Reject an invalid range or changed binding identity; never repair it with `min/max` or accept a bogus length. Add the two lifted ranges and a constructed range to getter regression tests.

## Effect mapping and exact fixtures

**High confidence in source rules, conditional on matching form and BIL.** Modern [`x86_tools_reg.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_tools_reg.ml) maps AL/AH/AX/EAX/RAX onto one `CPU.rax`; legacy [`assn_s`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_lifter.ml) likewise retains upper/lower old bits on partial writes and zero-extends 32-bit x86-64 writes. Thus preserved old bytes keep their origins; a whole-register `Move` in BIL does not automatically kill all RAX cells. Ariadne's [location contract](operand-effects-design.md#canonical-location-model) expands these views to `gpr:rax:0..7`, with an EAX write replacing all eight bytes. [BIL casts](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/lib/bap_types/bap_bil.ml) distinguish unsigned zero extension from signed extension, which reads the source sign bit.

Use independent expectations for forms observed in both modes: `4889d8` reads all RBX bytes and replaces all RAX bytes; `88d8` reads BL and replaces only RAX byte 0; `88dc` reads BL and replaces only RAX byte 1; `b878563412` replaces all RAX bytes and zeroes the high four; `488b448b08` reads RBX and RCX address bytes plus `memory:any` and replaces all RAX bytes; `488903` reads RBX address and RAX source bytes and may-writes `memory:any`. Modern [`x86_tools_mem.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_tools_mem.ml) builds addresses from base, scaled index, displacement, and applicable FS/GS base; legacy [operand and store construction](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_lifter.ml) must be reviewed independently for admitted address forms. A store cannot must-kill Ariadne's whole `memory:any` summary. These are proposed expectations, not passing comparisons against the helper and engine.

**High confidence in the conservative boundary; untested forms remain open.** Any empty-BIL form in the selected mode needs an explicit unsupported/opaque gap or an independently reviewed no-effect case. Production projection has no automatic LLVM effect fallback. A BIL `Move` to a flag does not by itself show that its value is defined: [`x86_tools_flags.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_tools_flags.ml) defines `set_unknown`, and [`x86_btx.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_btx.ml) uses it for flags. For admitted arithmetic, test defined, preserved, and undefined flags separately; ADC/SBB read CF, whereas INC/DEC preserve CF. Conditional writes read condition flags and are possible definitions, not automatic kills. PUSH/POP need implicit RSP and memory; Jcc/CALL/RET need typed control evidence. Ariadne's [call policy](operand-effects-design.md#memory-and-calls) keeps every call opaque over tracked locations with no definite kills, regardless of BAP jump or ABI metadata. LOCK/REP, address-size and segment overrides, malformed bytes, and unrecognized forms need exact-prefix guards; an opcode name alone is insufficient.

For **legacy** specifically, [`x86_lifter.ml`](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_lifter.ml) produces `RAX := extend:64[low:8[RAX]]` for the sampled MOVSX and nested zero padding for MOVZX; ADD/CMP update CF/OF/AF/PF/SF/ZF, ADC reads CF, LEA uses an address expression without memory, and NOT writes RAX without writing flags. Its CMOVNE sample is `RAX := Ite(~ZF,RBX,RAX)`: ZF is read, and the RAX destination is a possible write with no unconditional origin kill. Variable-count SHR reads RCX, and its nested `If` emits `Unknown[after-shift]` for AF and sometimes OF; zero count retains old flag values. Treat those unknown flag outputs as undefined only for reviewed exact forms, never infer that from a generic `Unknown`. A legacy Jcc is an `If` containing a `Jmp`; its condition is a flag dependency. CALL pushes a return address and jumps, but the BIL has no callee effect summary, so retain Ariadne's opaque call rule. RET reads stack memory and jumps to the popped target. The LOCK ADD diagnostic printed ordinary ADD BIL, and REP MOVSB contained `While`; neither may be admitted under an unguarded ordinary form rule. These observations propose positive and negative fixtures, not accepted semantics.

Further legacy negative probes make the escape hatches concrete: `0f05` SYSCALL lifted to one `Special call(syscall)`; `0fa2` CPUID wrote four GPRs with `Unknown[cpuid]` values; `0f0b` UD2 decoded as TRAP with **empty BIL**. The [legacy lifter source](https://github.com/BinaryAnalysisPlatform/bap/blob/baa9022/plugins/x86/x86_lifter.ml) has the CPUID unknown assignments, syscall special, and `No_semantics -> Ok []` path. A generic `Special` needs opaque effect/control handling, and an empty TRAP lift must never become ordinary fallthrough. CPUID's output cells are may-defined with unknown values; no concrete values can be inferred.

## Decision and next evidence

The evidence supports a tagged BIL walker. Legacy is the stronger **candidate** for the intended Stage 1 arithmetic/control corpus; source and diagnostics do not yet qualify it or make it the committed default. Modern remains useful as an earlier narrow-coverage comparison. Next retain a selected-build fixture record with bytes, VA, decoder name/length, raw BIL, getter outputs, projected effects/control, and independent expectations, including unsupported and prefixed negative cases. Carry source, build, plugin, and projection identity with every result.
