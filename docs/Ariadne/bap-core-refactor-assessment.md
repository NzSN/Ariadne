# Could BAP become Ariadne's core?

**Assessment, 2026-10-01.** The decision is whether the [Binary Analysis Platform (BAP)](https://github.com/BinaryAnalysisPlatform/bap) should replace Ariadne's Rust recovery and analysis core, or supply an alternative binary-semantics backend. The relevant workload is source-bound x86-64 crash investigation from captured bytes, with explicit uncertainty. This is a source and API assessment, not a BAP build, integration test, or runtime acceptance record.

The [two-stage BAP integration implementation plan](../../Plans/bap-integration.md)
specifies **Stage 1: semantic backend**, followed by **Stage 2: analysis core**.
Stage 1 is now implemented; its [historical BAP Stage 1 validation record](../../evidence/Ariadne/bap-stage1-validation.json)
keeps the missing historical Windows capture explicit. The subsequent
[LLVM semantic-backend removal](bap-only-removal-validation.md) makes BAP the
sole minidump semantic producer by user instruction. Stage 2 remains unstarted.
The [Stage 1 implementation design](bap-semantic-backend-design.md) now records
the native protocol and projection being implemented; qualification is separate
from this earlier source/API assessment.

## Decision in brief

**Technically possible in part; a core replacement is not justified yet.** BAP exposes raw-byte disassembly, instruction lifting, CFG reconstruction, BIL, BIR, and analysis passes. Those are credible inputs to a semantics comparison. They do not establish that BAP's output satisfies Ariadne's snapshot, effect, control, fault, and formal-evidence contracts. The lowest-risk decision is a **staged, pinned BAP backend experiment** behind Ariadne's existing request boundary. Retain the current core as the reference until representative captured cases and obligations have been compared. This recommendation is an architectural inference from the cited interfaces and local contracts, not a claim that the integration already works.

## What BAP actually supplies

**Raw input and lifting — high confidence for API existence, low confidence for Ariadne acceptance.** BAP's official README documents `bap mc` for supplied instruction bytes and the `raw` loader with an explicit base address for a code blob. Its OCaml API has `Memory.create` for a byte region at an address, `Disasm.of_mem` with an optional rooter (defaulting to the region's start), and `Disasm.Driver.scan` for a custom disassembly pipeline. The driver can classify memory and lift instructions into its knowledge base. This gives an entry point for Ariadne-owned captured spans, but does not itself preserve Ariadne's per-instruction capture evidence, sparse gaps, or snapshot identity. BAP's default driver is speculative: at barriers it can continue beyond a known path, and it may choose a still-classified code address when its worklist empties. Ariadne's builder instead follows only local known successors and retains unreadable or unsupported sites as gaps. A BAP-derived graph therefore needs explicit reconciliation before it could replace the current graph. [BAP README](https://github.com/BinaryAnalysisPlatform/bap#using), [Memory API](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Memory/index.html), [Disasm.of_mem API](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Disasm/index.html), [driver algorithm](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Disasm/Driver/index.html); Ariadne's [file-reader design](file-reader-design.md) and [request type](../../src/model.rs).

**Three IR names must stay distinct — high confidence.** BAP lifts machine instructions into **BIL**, with bitvector operations, `Load`/`Store`, `Unknown`, `Jmp`, and `Special` for semantics not expressible in BIL. It then builds **BIR**, whose program/subroutine/block/definition/phi/jump terms are organized for program analyses; BAP also offers an SSA transformation. Selecting an LLVM-backed BAP disassembler does not produce LLVM IR: instruction lifting is a separate semantic-provider responsibility, and neither BIL nor BIR is LLVM's `.ll`/`.bc` IR. Ariadne's [direct LLVM IR path](stage-e-completion.md) currently accepts separately supplied `.ll`/`.bc` after LLVM 20.1.2 verification. Replacing its input with BIR would change the subject of that acceptance, even if both representations contain SSA-like terms. [BAP overview and BIR terms](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/index.html), [BIL API](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Bil/index.html), [BAP API index, including SSA plugin](https://binaryanalysisplatform.github.io/bap/api/master/index.html).

**Dataflow is useful but does not discharge Ariadne's effect proof — high confidence in the mismatch.** BAP's BIL memory is an explicit `Load`/`Store` expression, and BIR definitions and phi nodes support data-dependency work. However, its documented BIL constant-propagation and dead-virtual passes explicitly do not track memory locations. BIL `Unknown` and `Special` are representational escape hatches, not evidence that an x86-64 instruction has a complete normal, fault, and undefined-output model. Ariadne needs a conservative projection onto byte GPR cells, individual flags, `memory:any`, and `state:other`, with distinct `uses`, `may_defs`, and `must_defs`; only definite replacement may kill an origin. A conditional write, undefined flag, unknown memory alias, or opaque call cannot be promoted to a definite kill because a lifted assignment appears in BAP. [BIL operations and special values](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Bil/index.html); Ariadne's [effect contract](operand-effects-design.md) and [validated request shape](../../src/model.rs).

**Control and calls need their own mapping — medium confidence for feasibility, high for obligation retention.** BIR distinguishes direct and indirect labels and has call, goto, return, and interrupt jump forms. That vocabulary can represent some of Ariadne's distinctions, but it is not a guarantee that BAP has enumerated every indirect target or modeled a callee's effects. Ariadne keeps incomplete indirect/call targets as obligations, excludes call-only edges from local traversal and stateflow, and initially treats a call as reading and possibly changing every tracked location with no definite kills. The current [machine-state engine](../../src/machine_state.rs) separately requires a trusted finite transition relation, including terminal outcomes and explicit adapter obligations for memory, exception, syscall, and concurrency gaps. A BAP CFG or lifted call alone supplies none of those completeness assertions. [BIR jump types](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/index.html); Ariadne's [effect design](operand-effects-design.md), [recovery model](../../src/model.rs), and [Stage E completion](stage-e-completion.md).

## Fit against Ariadne's evidence boundary

| Claim | Confidence | Basis and consequence |
| --- | --- | --- |
| BAP is a viable candidate **lifter or comparator** for captured x86-64 bytes. | High for capability; low for acceptance. | Official raw loader, `mc`, `Memory.create`, and disassembly APIs exist. No Ariadne corpus has been run through them in this assessment. |
| A BAP core swap would change trusted semantics and graph construction. | High. | The [current model](../../src/model.rs) consumes fixed snapshot VAs and normalized effects; BAP's [driver](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Disasm/Driver/index.html) performs its own classification and CFG recovery. |
| Existing Stage E evidence would remain evidence for its **current pinned source**, not for a BAP-backed result. | High. | [Stage E](stage-e-completion.md) records 32 cases, 64 complete traces, 326 observations, and 15 mutant mismatches for the existing Rust finite models and adapters. A changed producer or model requires fresh source-bound acceptance. |
| BAP would not automatically close Stage D's 0/49 instruction-step gate. | High. | The [historical user64 coverage ledger](../../Specs/AMD64/user64-coverage.json) requires decoded-form binding, effects/flags/frames, fault/commit and instruction-boundary proof, TLA–Lean correspondence, and conservative projection for each case. BAP's existence is additional trusted semantics, not those proofs. |
| BAP can replace Ariadne's directly verified LLVM IR path without a new contract. | Low; presently unsupported. | BIR is BAP's IR. Ariadne's [LLVM IR request](../../src/llvm_ir.rs) requires independently verified LLVM IR, artifact identity, memory predecessors, and call obligations. |

The captured-byte rule is particularly consequential. A minidump module record or matching executable path cannot fill missing runtime code bytes; Ariadne's [reader contract](file-reader-design.md) defaults to captured-only and forbids completing a captured prefix from file bytes. BAP's raw loader can consume a file or blob, but the caller must prove that each supplied instruction span came from the authorized snapshot. For a minidump with missing code pages, BAP cannot make those bytes known by choosing a different loader. This is a constraint on integration, not a criticism of BAP.

## Options and operational cost

| Option | Potential gain | Main cost or risk |
| --- | --- | --- |
| Keep the LLVM MC 20.1.2 decoder and Ariadne core | Preserves the currently exercised contracts and source-bound evidence. | Current rules deliberately lose precision on unfamiliar instructions and aliases. |
| Add pinned BAP as an **optional lifting/effect backend** | Compare BIL/BIR semantics with existing decoded facts; potentially gain coverage and targeted precision. | Needs a versioned OCaml/Rust boundary, provenance and obligation mapping, and fresh per-backend acceptance. |
| Replace recovery, dataflow, and stateflow with BAP | Could reuse BAP's broader analysis framework and CFG/IR tooling. | Re-derives Ariadne's formal refinement and report contracts, changes graph scope, and expands the trusted base. No source evidence yet shows this payoff exceeds the cost. |

BAP is primarily OCaml. Its README documents OCaml plugins, CLI use, and C bindings for other languages; a Rust integration could invoke a pinned BAP/OCaml helper over a strict protocol, or use bespoke C FFI. The former matches Ariadne's existing external-decoder pattern, while the latter adds runtime and ABI ownership work. A CLI `-d` dump may help exploration, but a production boundary would need stable machine-readable schema, errors, byte identity, and completeness fields; the README does not promise Ariadne's schema. [BAP README](https://github.com/BinaryAnalysisPlatform/bap), [project/pass API](https://binaryanalysisplatform.github.io/bap/api/master/bap/Bap/Std/Project/index.html).

Version choice is an open operational risk, not evidence that BAP is abandoned. The official [release page](https://github.com/BinaryAnalysisPlatform/bap/releases) labels **v2.5.0**, published July 2022, as latest stable, while the official [commit history](https://github.com/BinaryAnalysisPlatform/bap/commits/master/) shows source activity through May 2026. BAP documents both stable opam installation and a rolling/testing repository; its v2.5.0 notes explicitly mention LLVM 13/14 compatibility, and later source history includes LLVM 16/17 fixes. Ariadne's native decoder uses LLVM 20.1.2, so binary compatibility or co-installation with that version must be tested, not inferred. The public `master` API pages also contain since-2.6.0 annotations; treat those pages as evidence of available source interfaces, not proof that every interface ships in v2.5.0. [Install and build guidance](https://github.com/BinaryAnalysisPlatform/bap#installation), [v2.5.0 release](https://github.com/BinaryAnalysisPlatform/bap/releases/tag/v2.5.0), [source commits](https://github.com/BinaryAnalysisPlatform/bap/commits/master/), [Ariadne decoder design](operand-effects-design.md).

## Recommendation and next evidence

Run a **bounded backend experiment before any core replacement decision**. Pin an actual BAP version/build, feed only immutable captured instruction spans with their VAs, and compare BAP's decoded instructions, BIL/BIR, local edges, and unknowns against Ariadne's existing LLVM MC preparation on a selected corpus: register aliases and zero-extension, flags including undefined output, loads/stores, direct and indirect control, calls, unreadable gaps, and fault-sensitive candidates. Record where BAP's output can be conservatively projected to `uses`/`may_defs`/`must_defs`, where it must become an obligation, whether the requested platform can build and run, and the measured cost. Keep the captured snapshot and current Rust request/analysis path as the acceptance reference during that experiment. No such trial was performed here.

The recommendation could change if that experiment shows materially better coverage or precision with stable provenance and no unsound definite kills, and if the team is willing to own the pinned OCaml/BAP distribution. It could also turn negative if its default disassembly cannot be constrained to Ariadne's scope, if unsupported semantics are hard to expose, or if the target build cannot coexist with current LLVM tooling. Until then, BAP is a plausible **additional semantics source**, not a demonstrated replacement for Ariadne's core or a shortcut through its formal gates.
