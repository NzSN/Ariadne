Can the next frame’s return address narrow the possible values?

Yes, by constraining the relevant call context and, with additional reasoning, the paths compatible with the captured endpoint. A saved return address alone does not determine an internal JMP RAX target. Ariadne already uses it to select the active call; feeding that information back into target-value search would be a new feature.

Your idea can help a question such as “which values at this dispatch can lead to this captured frame/PC?” The resulting set is specific to that question. It cannot replace the resolver’s answer about every incoming state of the dispatch.

2. Two ways it could reduce possible values

Use the selected caller’s input constraints

The saved continuation selects a call site. Analyze the caller’s states at that call, derive justified argument constraints, then carry those constraints into the callee’s entry. If the dispatch depends on those inputs, its value set may shrink before considering a later endpoint:

saved return address → verified active CALL
                    → states/arguments at that CALL
                    → constrained callee entry states
                    → narrower dispatch values

Under the standard Windows x64 convention, the first four integer/pointer argument positions use RCX, RDX, R8 and R9. The return address contains none of their values. Caller analysis or correctly scoped saved-register evidence is still needed; crash-time volatile registers cannot simply become callee-entry values. Microsoft’s argument-passing contract; Ariadne’s observation scope.

For example, if accepted caller semantics prove the selected call passes a selector in {2, 3}, and the callee preserves or soundly transforms that constraint up to its dispatch, the dispatch need not start with every selector value. This is a hypothetical example; no such argument constraint has been proved for this dump. If the selector is freshly read from mutable memory in each loop iteration, an initial constraint may no longer restrict later iterations.

Use paths compatible with the selected endpoint

If a dispatch is in the caller before its active call, the validated call site can be the goal. For the remaining Case-4 dispatches inside frame 0, the relevant endpoint is instead the captured PC …43dd6e. The caller’s saved continuation …40410d sits outside that callee.

For a dispatch D visited before endpoint G in the same activation, the proposed question is:

Values_G(D) = { v |
  an admitted prefix reaches D with value v,
  and a compatible admitted suffix reaches G
}

Intersect forward value facts with backward constraints from G, preserving branch predicates and memory assumptions. If the table formula maps a selector to a destination proven unable to reach G, that selector can be excluded for this endpoint-specific question. Several selectors can still lead to the same destination, and several destinations can converge on the same endpoint.

For Case 4’s JMP RAX at …43da0e, the captured selector/table calculation supplies conditional destinations. All of them belong to the same runtime function, so identifying that function’s caller does not by itself distinguish them. The captured PC may support further constraints, but no reduced numeric selector set has been proved here. Retained dispatch arithmetic.

3. Why the cycle and budget limits still matter

cyclic-incoming-state is an unsupported repeated reverse-search context. resolution-work-limit is exhausted resolver work. They can coexist. In the retained Case-4 run, DA0E produced 271 infeasible prefix receipts, used the shared 2,097,152-step budget while rewriting guards, and left E200 without substantive work. A separate larger caller query later exhausted its core dataflow action budget. Cycle cutoff; Case-4 search explanation; separate caller-completion record.

Frame constraints can improve search ordering and sometimes produce stronger value constraints. They do not supply the missing loop invariant. In particular:

  • A destination absent from an incomplete graph is unknown, not disproved reachable to the goal.
  • No path found within a budget does not prove no path exists beyond that budget.
  • A branch may loop back and choose a different destination in a later iteration. The goal constraint must account for those iterations.
  • A dispatch need not lie on every route to the endpoint. Narrowing applies to visits that occur on the chosen question’s paths, not an assertion that the dispatch executed.
  • One compatible path cannot establish whole-dispatch coverage over all incoming states. Omitted paths cannot silently exclude possible memory writers.

The resolver currently receives snapshot/artifact identity, instructions, roots, BIL transfers, limits and captured-memory reads. It receives no frame-chain or endpoint constraint. Frame binding is a later consumer. Per-frame preparation supplies a function-entry root and, when requested, an ABI alignment premise; it does not specialize callee dispatch values from the selected caller’s argument state. Resolver interface; materializer call; per-frame preparation.

A useful next step is a separate endpoint-scoped refinement. Bind the verified call/crash-PC endpoint and activation to that query, use it first to prioritize promising work, and retain candidates as compatible, refuted or unknown. Hard exclusion needs checked backward constraints and loop reasoning. Existing global target receipts and their completeness claims stay separate.

For this particular budget failure, fair progress for short incoming prefixes and later dispatch sites is also important. An endpoint heuristic should help that scheduling, while still giving other contexts bounded progress. The ordinary table witnesses must be obtained before the current loop rule can use them.
