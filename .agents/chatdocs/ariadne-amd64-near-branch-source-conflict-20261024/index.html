Does 66h change a near branch to a 16-bit operation in native 64-bit mode?

The selected AMD manual gives two incompatible general answers. Its near-branch table permits a 16-bit override, while the following page makes the operand size and several effects unconditional at 64 bits. P2-C must reconcile that applicability before claiming complete source rules.

The uncertainty concerns the prefixed cases. The common default-64 rule is agreed. A 64-bit-only execution target still needs the applicable smaller-operand forms inside that mode. This source conflict does not establish that ordinary AMD64 calls are unsupported or that processor behavior is inherently unknowable.

1. The exact conflict, on adjacent pages

Table-side interpretation

Default 64; override 16 is permitted

Vol1 Table 3-9 puts 64 in the default-size column and 16 in its shared override column for seven near-branch groups. The earlier default-size discussion connects the 16-bit choice with prefix 66h.

Vol1 PDF 128, printed 90, cells pdf:128:cell:32–36; earlier discussion: PDF 114, printed 76, cells 9–12.

Following-prose interpretation

Operand size remains fixed at 64

The next page calls the near-branch operand size fixed at 64 bits. It also says four listed effects are forced to 64: instruction-pointer truncation, CALL/RET stack-transfer size, their stack adjustment, and the indirect-target operand.

Vol1 PDF 129, printed 91, cells pdf:129:cell:5–18.

Why this is a conflict: a default leaves room for a permitted exception; an unconditional fixed-size rule removes that exception. Applying both descriptions to the same 66h-prefixed form cannot determine a single operand-size contract. One of the statements needs a narrower scope, a qualification, or a correction.

The PDF has a shared 16 cell spanning the branch groups. Its position is visible in the rendered page. The disagreement survives checking physical geometry and the next page's prose, so repairing text extraction cannot resolve it. Vol3's default-64 list also permits a 66h-to-16 override. Vol3 Table B-5 and following text, PDF 655, printed 613.

2. Four different widths must remain separate

PropertyWhat it controlsHow it relates to this question
Execution modeThe processor's native AMD64 instruction environment.H64 selects this mode. An operand override is an instruction property within it.
Effective operand sizeThe width used by the form's operand and its specified effects.The table/prose disagreement is whether 66h can change this width for the relevant near-branch form.
Address sizeAddress calculations and selected implicit register widths.The existing native-64 source contract has 64-bit and address-32 cases. Prefix 67h selects address size; it is a separate rule from 66h.
Encoded displacement sizeThe number of bits stored in a relative branch's instruction bytes.A 64-bit target calculation can use a signed 8- or 32-bit displacement. It does not require an encoded 64-bit displacement.

Instruction-owned context: Vol3 CALL (Near), PDF 178; JrCXZ, PDF 249; LOOP family, PDF 269. These sources help separate the properties; their generic and mode-specific descriptions still need form-level reconciliation.

Why H64 does not remove the question: supporting native-64 execution leaves byte, word and doubleword operands in scope whenever their forms are valid in that mode. Excluding every 16-bit operand would be a new instruction-form scope decision. The hypothesis accepted so far only excludes non-64 execution modes.

A normal relative CALL already mixes widths

For an ordinary unprefixed E8 form, the current source contract uses a signed 32-bit displacement in a 64-bit target calculation. Consider a supplied next-instruction address of 0x0000000140001005 and displacement +0x20:

target = next_RIP + sign_extend_64(displacement32) = 0x0000000140001025

Both source readings can agree on this default case. The disputed applicability of 66h is an additional question.

3. The seven groups are an inventory to review individually

The shared table cell creates a broad conflict, but it does not prove identical prefix behavior for every opcode. Direct, indirect, short-relative and stack-return forms need their own records.

4. Why the choice matters to an analyzer

The consequence is a different control/data-flow contract. Treating a prefix as an override can change which input bits contribute to a target, which memory bytes hold a return address, and how the stack pointer changes. A report built on the wrong contract could recover a different successor or connect a dependency to the wrong memory interval.

Conditional model example. The following arithmetic illustrates the consequences of two candidate width rules for an indirect near CALL. It assumes a normal, nonfaulting transfer with readable/writable memory. It does not decode a concrete prefixed byte sequence or report a CPU experiment.

6. What would resolve it, and what work can continue

An authoritative source interpretation

Find an AMD correction or explanation identifying which near-branch forms accept 66h, what changes, and what the fixed-size wording was meant to cover. Bind the answer to an edition and exact forms, then replay the preserved source relationships.

A declared implementation hypothesis with scoped validation

A chosen source-precedence policy could permit conditional implementation work. The policy must state its premise and target CPU/form scope. A useful validation matrix distinguishes direct/indirect and short/near forms, 66h presence, 67h interactions, relevant register extensions and normal/fault outcomes. Actual byte decoding, CPU identification and measured effects are required to claim that the matrix was exercised.

Such a hypothesis can organize engineering progress while the publisher inconsistency remains recorded. A decoder's output, an emulator's behavior or a different vendor's CPU is evidence with its own scope, rather than automatic resolution of the selected AMD source.

A deliberate instruction-form scope restriction

Supporting only specified unprefixed branch forms would be a narrower deliverable than H64 alone. It would need an explicit scope delta, preserved excluded cases and matching tests. It cannot retroactively make an older, wider P2 source review complete.

Work that can proceed now: inventory the exact affected forms and source links, preserve the agreed default-64 cases, continue unrelated prefix and instruction reviews, and keep the disputed forms explicit. The source question blocks a claim of fully reconciled near-branch override rules; it does not prevent all P2 engineering.

Concrete question for an authoritative follow-up

For AMD64 native 64-bit execution, what are the legal operand sizes and effects of prefix 66h for each near CALL, Jcc, JrCXZ, JMP, LOOP/LOOPcc and RET form? How should Vol1 revision 3.25 Table 3-9's 16-bit override column be reconciled with the next page's fixed-size and forced-action statements? Specify instruction-pointer truncation, indirect-target width, CALL/RET return-slot width and stack adjustment, including interactions with address-size selection.

This is a prepared question only. No message has been sent to AMD or anyone else.
