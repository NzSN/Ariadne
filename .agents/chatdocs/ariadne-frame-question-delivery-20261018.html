What you now have

The earlier structural product recovered frame anchors, admitted local control flow and explicit unknown frontiers. The connection product added reachability, cycle groups and example routes. This delivery lets an investigator spend bounded semantic work on one question about that source, without first completing every caller’s dataflow analysis.

Existing productsA partial map of the captured activations and represented connections, with gaps and independently bounded route examples.
New question productA selected alternative checked against value constraints, or a local fault-dependency assessment with value facts, possible memory origins and reasons for stopping.

The entry point is --frame-question QUESTION.json. It writes frame-question.json, frame-question.txt and frame-question.dot. The JSON embeds the source and evidence needed to replay its assessment. Library users can provide an already bound structural source or connection source.

Delivery scope: the new code integrates recommendation items 5.1–5.4. The structural and connection engines already existed in the preceding delivery; this commit reuses them and adds the focused question, scheduling, constraint, dependency and replay layers.

Two kinds of question

1. Can this alternative coexist with these value constraints?

Select a represented edge and a register constraint at an exact before or after point. For example: “Can this taken branch lead to the selected endpoint with RCX equal to zero, under the declared normal-flow model?” Supported explicit conditions can narrow the question further.

AnswerWhat it means
possible_under_modelA separately checked, coherent concrete assignment and loop-free model path satisfy the supported relations. This establishes a model witness.
refuted_under_modelThe alternative is incompatible within the declared model and covered scope. A stopped search or missing semantics cannot produce this conclusion.
unknownThe bounded analysis cannot settle it. The report names missing relations, open frontiers, work limits or unavailable cycle/value coverage. Abstract nonemptiness alone also remains unknown.
premise_conflictValid supplied conditions conflict with admitted observations or premises. The conflict is reported explicitly.

The compiled diamond fixture demonstrates the distinction: one endpoint RCX value has a model witness; changing that value refutes the selected branch in the supported fixture model. Zero work produces an explicit unknown.

2. Which local values and possible writers contribute to this access?

Select a frame, instruction address and access index. The result separates captured observations from earlier facts derived through checked transfers. It walks register producers to contributing load boundaries, then preserves and assesses the actual baseline memory origins from the compatible completed callee.

A requested writer is a focus hint; it does not filter the candidate universe. Numerical work and origin assessment have separate receipts, so useful facts can remain available when another layer stops. This question profile does not use the branch-feasibility verdict as its success measure; feasibility is marked unavailable / not applicable.

A model witness is not an execution record. The current profile reports execution evidence as not_supplied. Captured registers describe the captured point; earlier branches, argument values, iterations and writers need their own evidence.

How the implementation is arranged

Fair work: the resolver rotates admitted tasks through question, relevant and coverage bands in a 2:1:1 schedule, with FIFO service within each band. Sufficient work gives peers turns; finite task, work and byte caps still apply. Deadlines are cooperative boundaries around bounded operations.

Checked scalar scope: the first profile uses 64-bit general-purpose register constraints, known-bit masks and supported constant/copy/add/subtract/AND relations. BAP remains the source of minidump semantics. Unsupported flag relations, memory inversions and partial-register combinations retain uncertainty.

Source revisions: independently admitted successors keep the same snapshot, roots and selected range. A revision has its own identity; stale conclusions and incompatible completed-callee imports are invalidated or recomputed.

Saved verification: the strict ariadne.frame-question/v1 decoder replays source admission, revisions and conclusions using a BAP-only build, without reopening the capture, launching helpers or fetching from the network. An independently trusted expected binding identifies the intended publication; internal hashes alone do not authenticate a capture.

How to use the delivered mode

The following is the documented finite-diamond example. It asks about a taken edge in frame 1 and RCX = 0 before its endpoint. Save the JSON as question.json; register bank 1 is RCX in the existing AMD64 namespace.

{
  "schema": "ariadne.frame-question-request/v1",
  "from_frame": 1,
  "to_frame": 0,
  "question": {
    "question": {
      "kind": "alternative",
      "frame": 1,
      "site": "0x0000000000400306",
      "destination": "0x000000000040030c",
      "edge_kind": "taken",
      "endpoint": {
        "point": {
          "frame": 1,
          "site": "0x0000000000400310",
          "moment": "before"
        },
        "bank": 1,
        "width": 64,
        "mask": "0xffffffffffffffff",
        "value": "0x0000000000000000"
      }
    },
    "conditions": []
  }
}
cargo run --offline --locked --bin ariadne-minidump -- \
  tests/input/fixtures/frame_paths/diamond.dmp \
  --decoder-reference target/ariadne-llvm-mc \
  --frame-question question.json \
  --output-dir target/my-frame-question

Live analysis needs the configured BAP lifter/runtime and LLVM reference helper. Use a new output directory. An optional --frame-question-limits POLICY.json supplies the complete finite policy. The canonical usage section defines the supported vocabulary and library interfaces.

For fault dependencies, use kind: fault_dependency, with frame, site, access, optional load and optional focus_writer. The retained controlled request is an exact example for that capture. Addresses and masks are canonical 16-digit hexadecimal strings.

What remains open

The local implementation and local product acceptance are delivered. The P0–P8 stages and local P9/P10 clauses are recorded as passed. Full program acceptance still depends on the separately named gates.

  • Remote Windows WSL qualification: P9 and imported FC5/M4 remain open. The retained receipt records the missing registered executor, launcher and SSH host configuration for that campaign.
  • Broader campaigns: full Scanner qualification, caller S6, frame-path F4 and release qualification remain separate.
  • Semantic scope: v1 has no general SMT solver, general cross-activation argument proof, historical memory inversion or general loop-instance value proof. Unsupported relations stay unknown.
  • Historical claims: the delivery supplies no execution recording, executed-writer identity, iteration count, lifetime-violation proof or root-cause conclusion.

The next qualification work is to provide the declared remote prerequisites and run the named P9 / FC5 / M4 clauses. Further semantic work should target a concrete remaining obligation, such as a required loop-value invariant, with its own checked contract and evidence.
