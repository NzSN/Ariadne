H64: support native AMD64 64-bit execution only

For this AMD64 program, the new hypothesis excludes legacy and compatibility-mode execution and 32-bit/WOW64 target execution. It retains instruction forms that execute in native 64-bit mode, including their smaller operands.

The frozen source scope already selects long-64. H64 makes the intended target and mode-specific exclusions explicit. It does not mean every operand, address or encoding field is 64 bits.

A 64-bit analysis host does not establish that the input is a native-64 target. Target architecture and captured context must govern that selection. The current reader checks AMD64 system information and matching context types; this hypothesis update adds no new runtime enforcement or qualification.

What this changes for P2-C

C can focus its required execution-mode inventory on native-64 rows, treating explicitly non-64-only material as source-preserved out-of-mode context after ownership is checked. Shared notes and mixed-mode tables still need enough review to establish which constraints apply to the native-64 rows.

The five current roots remain relevant: 66h opcode/operand roles, LOCK eligibility, F2/F3 repetition versus opcode selection, default-size exceptions, and exact default-64/fixed-size instruction forms. H64 does not remove native-64 32-bit defaults, 16-bit operand overrides, byte forms, address-32 overrides or applicable SIMD prefix rules.

The GF question remains in scope

GF inverse operations on byte elements also have instruction forms used in 64-bit execution. Narrowing the execution mode does not remove the published F1 → 5B lookup issue. Feature availability and privilege requirements likewise remain separate conditions.
